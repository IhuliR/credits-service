# Инженерные решения

Документ фиксирует транзакционные границы, механизмы конкурентного доступа и известные ограничения Credits Service. Источником истины остаётся код и миграции проекта.

## Транзакции и Unit of Work

Сценарии записи выполняются через Unit of Work. Изменения MySQL считаются завершёнными только после явного `commit`; выход из блока без успешного commit приводит к rollback. Внешние операции с Redis, RabbitMQ и provider не включены в транзакцию MySQL.

## Purchase webhook

### Идемпотентность начисления

Предварительная проверка `exists → insert` не защищает от двух конкурентных запросов: обе транзакции могут одновременно не увидеть событие. Поэтому `purchase_events.event_id` имеет DB-level ограничение `UNIQUE` с именем `uq_purchase_events_event_id`.

Добавление purchase event, увеличение баланса и положительная ledger operation типа `purchase` выполняются в одной транзакции. Репозиторий делает `flush`, распознаёт только MySQL duplicate-key error для этого конкретного ограничения и преобразует его в доменную `DuplicatePurchaseEventError`. Остальные `IntegrityError` не маскируются как дубликат.

Повторная доставка возвращает штатный результат `duplicate`; неуспешная транзакция не оставляет частичное начисление или ledger operation.

### Redis balance cache

После успешного commit purchase кэш баланса пользователя инвалидируется. Redis не меняется до фиксации MySQL. Duplicate-доставка также инвалидирует ключ: это позволяет убрать потенциально устаревшее значение после уже обработанного события.

MySQL и Redis не образуют общую транзакцию. Сбой процесса или Redis после commit может оставить старое значение до истечения `BALANCE_CACHE_TTL_SECONDS`.

## Создание Generation

Баланс пользователя читается методом репозитория с `SELECT ... FOR UPDATE`. В одной транзакции выполняются:

1. блокировка строки баланса и проверка достаточности средств;
2. уменьшение баланса;
3. создание Generation в статусе `pending`;
4. отрицательная ledger operation `generation_debit`;
5. commit.

Конкурентный запрос того же пользователя ждёт освобождения строки, затем читает уже уменьшенный баланс. Если средств осталось недостаточно, Generation и debit для второго запроса не создаются.

Для пользователя без строки баланса доступный баланс считается нулевым, поэтому Generation создать нельзя. Первая покупка создаёт или обновляет строку баланса.

После commit API публикует `generation_id` в RabbitMQ и затем инвалидирует Redis. Такой порядок не позволяет worker прочитать Generation до того, как она станет видима в другой MySQL-сессии, и не публикует сообщение при ошибке commit.

Остаётся dual-write окно `commit → publish`: при сбое процесса или RabbitMQ после commit Generation останется `pending` без сообщения. Кроме того, ошибка publish происходит до инвалидации кэша в текущем сценарии. Transactional outbox и повторная доставка неопубликованных задач не реализованы.

## Lifecycle worker

Основной переход состояний:

```text
pending --claim--> processing --provider success--> completed
                            \--final error-------> failed + refund
```

### Атомарный claim

Worker открывает короткую транзакцию, читает Generation через `SELECT ... FOR UPDATE`, проверяет статус `pending`, переводит запись в `processing` и делает commit. Повторная или конкурентная доставка после этого видит состояние, отличное от `pending`, и не вызывает provider.

DB-lock освобождается до внешнего вызова. Provider, таймауты и backoff не удерживают MySQL-транзакцию и соединение с блокировкой строки.

### Вызов provider, timeout и retry

Каждая попытка ограничена `PROVIDER_TIMEOUT_SECONDS` через `asyncio.timeout()`.

- `ProviderTemporaryError` и timeout повторяются до `PROVIDER_MAX_ATTEMPTS`.
- `ProviderPermanentError` не повторяется.
- Задержка перед следующей попыткой равна `base_delay × 2^(attempt - 1)`; jitter отсутствует.
- После успешного ответа Generation переходит в `completed`, а URL результата сохраняется отдельной короткой транзакцией.

При настройках по умолчанию выполняются не более трёх вызовов с таймаутом пять секунд и две задержки — одну и две секунды. Худший штатный timeout-сценарий занимает примерно 18 секунд.

### Failed и refund

После постоянной ошибки или исчерпания попыток worker снова блокирует строку Generation. Только для текущего статуса `processing` в одной транзакции выполняются:

1. переход в `failed` и сохранение текста ошибки;
2. увеличение баланса на `generation.cost`;
3. положительная ledger operation `generation_refund` с `reference_id` Generation;
4. commit.

Текст ошибки обрезается до 512 символов в соответствии со схемой MySQL. При ошибке commit статус, баланс и ledger operation откатываются вместе. Redis инвалидируется только после успешного commit.

Идемпотентность refund обеспечивается состоянием Generation в сочетании с row lock. После первой успешной компенсации статус уже `failed`, поэтому повторная доставка не создаёт ещё один refund. Отдельного `UNIQUE` idempotency key для ledger operations нет.

Ожидаемые provider errors и timeout полностью завершаются внутри use case. Неожиданные ошибки MySQL, Redis, RabbitMQ и другие инфраструктурные исключения не проглатываются обработчиком.

## Миграции

Начальная ревизия `0001_initial` сохраняется неизменной. Ревизия `0002_unique_purchase_event_id` заменяет обычный индекс `purchase_events.event_id` на уникальное ограничение.

Если существующая база уже содержит повторяющиеся `event_id`, применение `UNIQUE` завершится ошибкой. Перед миграцией такой базы нужна отдельная контролируемая процедура поиска дублей и финансовой сверки. Миграция намеренно не удаляет исторические записи и не корректирует баланс автоматически.

## Что проверяют тесты

Unit-тесты подтверждают:

- обработку нового и повторного purchase event;
- инвалидацию кэша только после commit;
- использование repository-методов `get_for_update`;
- порядок `commit → publish`;
- success, temporary retry, permanent failure, timeout и исчерпание попыток provider;
- число вызовов provider и экспоненциальные задержки;
- повторную доставку завершённой Generation без второго вызова provider или refund;
- атомарность refund на уровне поведения fake Unit of Work, включая commit failure;
- ограничение сохранённого текста ошибки;
- распознавание конкретного MySQL duplicate-key error в purchase repository.

In-memory fakes не воспроизводят блокировки, уровни изоляции и конкуренцию реальных MySQL-сессий. Для полной проверки нужны интеграционные сценарии с реальной MySQL:

- два одновременных webhook с одним `event_id`;
- два одновременных создания Generation при балансе только на одну;
- две конкурентные доставки одного `generation_id`;
- rollback транзакций и видимость изменений между отдельными соединениями.

Compose smoke-тест дополняет unit-тесты проверкой миграций, подключений к MySQL/Redis/RabbitMQ, доставки задачи worker и доступности HTTP API.

## Известные ограничения

- Нет transactional outbox между MySQL и RabbitMQ.
- Нет reconciler для Generation, зависших в `pending` или `processing` после падения процесса.
- Если provider успешно завершил работу, а worker упал до сохранения результата, автоматическое восстановление отсутствует.
- Нет отдельной управляемой transport retry/requeue policy для неожиданных инфраструктурных ошибок.
- Retry выполняется внутри worker и занимает consumer на время provider timeout и backoff.
- Нет jitter, circuit breaker, rate limiting и provider-side idempotency key.
- MySQL commit и Redis invalidation неатомарны; при сбое кэш может быть устаревшим до TTL.
- DB-level уникальность refund ledger не добавлена; гарантия опирается на статус Generation и row lock.
- Нет интеграционных конкурентных тестов с несколькими реальными MySQL-сессиями.
